# check

## 范围

- 先确认是哪个仓库：工作区本身在根目录；app 用 `git -C apps/<app>`。没说是哪个，就看这次改动在哪边
- 默认查这次对话里改过的东西。我指定了文件或目录，就查那些
- 查到的东西有牵连的也查：它调用的、调用它的、写到它的文档和规则
- 我说「全部」「整体」「所有」「从头」时，或者这次对话里还没改过东西时，查工作区本身所有没提交的改动（`git diff --cached`、`git diff`、`git status --short` 里的新文件），不管是谁改的。不查 `apps/` 里的 app，我点名了才查

## 依据

- 判断对错只看这几样：组织规定、`.claude/` 里的规则、我定过的决定、实际跑出来的结果、工具的官方文档
- 别的项目（比如 game-workspace）怎么做的，不算依据
- 看不出为什么这么做的地方，先问我。不自己编理由，也不直接当成问题

## 怎么查

- shell 脚本：先跑 `bash -n`。改了逻辑的，再在 scratchpad 里建副本，跑受影响的 make 命令，看输出和退出码。只改了注释的，`bash -n` 就够。测试要守的规矩见 CLAUDE.md 和 `style.shell.md`
- 规则：改到的文件，按它适用的 `style.*`、`dir.*` 逐条对照
- 引用：删掉或改名的文件、函数、变量、命令，用 `grep` 查一遍还有没有地方在用
- 文档：命令、流程、目录有变化时，看 `dev/docs/`、README 和 `.example` 里的说明有没有跟着改
- `.claude/`：rule 的 `paths:` 能不能匹配到它要管的文件；CLAUDE.md、rules、skills 之间有没有重复或矛盾
- app：跑它 README 里写的检查命令

## 什么算问题

- 跑起来不对：报错、输出不对、退出码不对
- 违反规则，或者两条规则互相矛盾
- 文档、注释和实际情况对不上
- 还留着的引用，没人用的东西
- 下面这些不算问题：换种写法更好、我觉得应该怎么写。我问建议时再说

## 汇报

- 按 CLAUDE.md「回答」那节：没问题就一句「没问题」
- 有问题时一条一个：`文件:行`、哪里有问题、依据（哪条规则，或者跑出来的输出）
- 没跑到、没验证的地方，最后单独用一句说
- 只报不改。等我说改了再改
